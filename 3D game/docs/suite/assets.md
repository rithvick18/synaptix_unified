# Assets and environments

The suite's 3D content is packaged locally under `public/suite/`, and nothing is hotlinked at runtime.

| What | Where |
|---|---|
| Asset manifest | `public/suite/assets/manifest.json` |
| Procedural builders | `src/suite/assets/builders/*.ts`, registered in `builders/index.ts` |
| Scanned models (CC0, Poly Haven) | `public/suite/assets/models/*.glb`, packed by `tools/suite/assets/fetch-models.mjs`, which records each source in `models/sources.json` |
| Shells (the rooms) and their slots | `src/suite/environments/shells/{livingRoom,kitchenDining,courtyardVeranda}.ts` |
| Photographed places (a real 360° capture as the environment) | `src/suite/environments/shells/photo.ts` (`photoShell`), one config per place under `src/suite/environments/shells/photo*.ts` |
| Panoramas | `public/suite/assets/panoramas/<name>.webp` and `<name>_1k.hdr`, vendored by `tools/suite/assets/fetch-panoramas.mjs`, which records each source in `panoramas/sources.json` |
| Scene builder | `src/suite/environments/index.ts` (`buildSuiteScene`) |
| Environment dressing presets | `public/suite/packs/<pack>/environments.json`, written by `tools/suite/assets/write-environments.py` |
| Textures (CC0, Poly Haven) | `public/suite/assets/textures/`, where `sources.json` records the source of every file |
| Thumbnails | `public/suite/assets/thumbs/<id>.webp`, rendered by `tools/suite/assets/render-thumbnails.mjs` |
| Provenance | `public/suite/assets/ATTRIBUTION.md` |
| Real photographed-object hotspots | `SlotDef.photoHotspot` and manifest assets with `source.kind: "photograph"`; generated by `tools/suite/assets/write-photo-hotspots.py` |
| How a place looks | `tools/suite/assets/screenshot-environments.mjs <out-dir>` screenshots every starter environment through `preview.html`, with the game's own renderer; `shell:<id>`, `--grid=1`, `--slots=1`, `--probe=1` and `look:` views help place a photo room's slots |

## Add an asset

1. **Write the builder.** Add a builder to a file in `src/suite/assets/builders/` and register it in `builders/index.ts`. Follow these conventions:
   - put the origin at the base centre, with +Z as the front;
   - work in real-world metres;
   - use palette materials through `Kit`, which caches and reference-counts them;
   - render text such as a calendar month at runtime, through `runtimeText` in the active language, never baked into a texture.
2. **Add a manifest entry.** Fill in the id, category, mount, `source.builder`, and label and description in English and Hindi (the Hindi is marked as needing review). Also fill in `size` as the built bounding box, `collision`, `activities`, `topics`, `provenance` and `budget`. A region-specific item also needs `tags.regions` and `descriptionSources`, the sources where its description was checked. Keep the description short and factual, and never claim that everyone in a region uses the item.
3. **Render and check.** Run `node tools/suite/assets/render-thumbnails.mjs`, then `npm run check -- suite-assets`.

An external model is allowed only with a verified redistributable licence (CC0 is preferred). Record it in `provenance` and in `ATTRIBUTION.md`, keep it under 3 MB, and give it a procedural `fallback`.

To use a Poly Haven model, add a line to `MODELS` in `tools/suite/assets/fetch-models.mjs` and run the tool. Give the line a `fit` box taken from the limits of the slots the asset is placed in. Add `height` if other objects stand on the model, because a host's height must stay exact. The tool packs the model with small WebP textures and sizes it to fit. The asset's old procedural entry is kept as `<id>-simple`, which is the model's `fallback`. The low tier, the node checks and any failed load use that fallback. After the tool, render thumbnails and run the check as in step 3. Pick models that look like the homes the packs describe; most of Poly Haven's catalogue does not.

## Add or change an environment

An environment is a list of placements in a pack's `environments.json`, and each placement puts one asset in one slot of a shell. A slot accepts one mount (`floor`, `wall` or `surface`) and has a `maxSize`. A `surface` slot with a `host` sits on the furniture that is placed in the host slot, and that furniture must be the stated height: for example, the living room's `centre-top-left` needs a 0.42 m table in `centre`. Edit `tools/suite/assets/write-environments.py`, which validates every placement before writing the file, and then run the check.

## Add a photo room

For a place with no rendered props, identify landmarks already visible in the panorama with `photoHotspot: { u, v, width, height }` on each slot. Create matching manifest entries with `source.kind: "photograph"`, a crop from the source panorama as the thumbnail, and source-specific provenance. The scene builder places an invisible ray target over each photographed landmark, preserving the existing activity and keyboard-list behavior. The photographed-place picker uses this mode for both indoor and outdoor captures.

A photo room is a real 360° photograph of a room, with the suite's 3D objects standing on its floor, sitting on its tables and hanging on its walls. The objects are lit by the same place's HDR, and on the standard tier they cast shadows onto the photograph's floor. A photograph is right only from where it was taken, so the seat is the camera's lens: walking stays within a small parallax radius of it, and a closer look at an object is a narrower view from near the seat rather than a walk up to it.

1. **Vendor the panorama.** For a Poly Haven HDRI, run `node tools/suite/assets/fetch-panoramas.mjs <polyhaven-id> [--name=<name>]`. For a panorama from another site, pass its Radiance `.hdr` of any size with its licence: `--hdr=<file> [--display=<tone-mapped jpg/png>] --name=<name> --title=… --author=… --license=<SPDX> --url=<page>`. Without `--display`, the backdrop is tone-mapped from the `.hdr` with the renderer's own ACES curve. The tool writes `panoramas/<name>.webp`, which is the backdrop at 3840 × 1920, and `panoramas/<name>_1k.hdr`, which is the light. It also records the source in `panoramas/sources.json`. Add both files to `ATTRIBUTION.md` by hand. Pick a photograph of a room with clear floor in front of the camera, because objects can only stand in front of what was photographed, never behind it.
2. **Write the shell.** Create `shells/<shellId>.ts` that exports `photoShell({...})`, and register it in `shells/index.ts`, in `ShellId` (`src/suite/contracts.ts`) and in `SHELL_IDS` (`src/suite/content/validate.ts`). Fill in these fields:
   - `panorama.display` and `panorama.lighting`: the two files, as paths under `public/suite/`.
   - `panorama.cameraHeight`: the lens's height in metres. To measure it, find a door (about 2.0 m) in the image, and read the elevation angles of its top and bottom (row fraction v gives π(0.5 − v)). Then cameraHeight = 2.0 / (1 + tan(top) / tan(−bottom)).
   - `panorama.yaw`: the turn that puts the room's front ahead of the seat, along −z. `2π(u − 0.5)` puts image column u (a fraction of the width) straight ahead. Choose the column that makes the main wall square to the view.
   - `panorama.exposure`: multiplies the HDR's light on the objects. The default is 1. Tune it with `--probe=1` until the matte white ball looks as bright as white things in the photograph.
   - `panorama.key`: the photograph's main light (usually a window) as `{ azimuth, elevation, intensity, softness }`, for direct light and shadows. A light at column u and row v has azimuth = 2π(u − 0.5) − yaw and elevation = π(0.5 − v). Raise the elevation above the window's own angle so that shadows stay short.
   - `panorama.radius`: the sphere the walls are projected on. The default is 7 m. The floor is flat out to about cameraHeight / tan(asin(1.5 · cameraHeight / radius)).
   - `parallax`: how far (m) the eye may move from the lens. The default is 0.25 m. Things photographed 1 m away shift about 10° for every 0.2 m of movement.
   - `floor`: the clear floor, as [minX, minZ, maxX, maxZ], where shadows may fall. A shadow drawn over a photographed wall or sofa gives the trick away.
   - `target`: where the seat looks.
   - `slots`: as for any shell, in metres, with the seat at (0, cameraHeight, 0) above the origin. Floor slots go on clear floor, at least parallax + 0.45 m from the origin. Wall slots go on the photograph's measured wall planes.
3. **Place the slots against the photograph.** Run `node tools/suite/assets/screenshot-environments.mjs <out-dir> shell:<shellId> --grid=1 --slots=1 --views=seat,look:0,-30,look:90,-30,look:180,-30,look:-90,-30`. The grid is the floor in metres, as the photograph projects it: a room's walls meet the floor where the grid runs into them. The boxes are every slot's `maxSize`. For a pixel in the photograph, `panoramaFloorPoint(u, v, yaw, cameraHeight)` gives the floor point in metres. Adjust the slots until the boxes stand on clear floor and flat against the walls.
4. **Dress it.** Add a preset with the new shell to the pack in `tools/suite/assets/write-environments.py`. The shell's materials do not apply to a photo room, so pass `{}`. Run the script, then `npm run check -- suite-assets`, which checks photo rooms' files, viewpoints and walking. Finally, screenshot the preset with `--views=all`.

The seat is the lens, so every object's viewpoint is the seat moved at most `parallax` toward the object and zoomed (`viewpoint.fov`, 28–60°) to frame it. The close-up zooms further in rather than moving the camera. Floor objects get a soft contact shadow, which is also drawn on the low tier. The backdrop ignores the renderer's tone mapping: on the full tier, where OutputPass tone-maps the whole frame at the end, the backdrop writes the inverse of ACES, so the photograph still comes out exactly as photographed. It takes no part in the ambient occlusion pass, because the inside of a sphere reads as one deep crease; the shadow-catching floor plane stands in for it.

## Budgets

The limits for a standard-quality environment are 180 draw calls, 250k triangles and 48 MB of textures. Measured in the browser with textures and the scanned models loaded, the starter environments come to:

| Environment | Objects | Photo surfaces | Triangles | Meshes | Textures |
|---|---|---|---|---|---|
| everyday-home/living-room | 25 | 6 | 31,142 | 110 | 31.6 MB |
| everyday-home/kitchen-dining | 28 | 2 | 44,800 | 95 | 42.8 MB |
| everyday-home/courtyard-veranda | 24 | 2 | 105,488 | 99 | 45.9 MB |
| northeast-home/ne-living-room | 25 | 6 | 49,092 | 103 | 33.6 MB |
| northeast-home/ne-veranda | 24 | 2 | 132,350 | 95 | 47.5 MB |
| everyday-home/photo-living-demo | 7 | 1 | 92,626 | 27 | 44.1 MB |

A photo room's textures are mostly its backdrop, 28.1 MB for 3840 × 1920 RGBA8 without mipmaps. It is seen at about one texel per pixel at the suite's 70° field of view, so mipmaps would add a third for nothing. Its light adds 1.5 MB: the PMREM is made from the 1k HDR halved, the same size as a modelled room's captured reflections. That leaves about 18 MB for the objects. The low tier draws a 1920 × 960 backdrop (7 MB). The backdrop sphere is 16k triangles.

`npm run check -- suite-assets` measures the same environments headless, with flat materials and the procedural fallbacks, so its triangle counts are lower. Prototypes are built once and shared by reference count, so they are cloned rather than rebuilt, and `dispose()` releases them. The `low` quality tier has no shadow maps.

## Lighting

Rooms and the house draw through one renderer (`src/Renderer.ts`). On the `full` quality tier it adds screen-space ambient occlusion (GTAO), which darkens contact points and corners. The software and baseline tiers draw without it. An interior shell's sun comes in through its windows: the walls, ceiling and window grills cast shadows, so the sunlight falls on the floor as a patch with bar shadows. The hemisphere fill keeps the rest of the room bright, because a dim corner hides what is in it. Once a room is on screen, the suite captures it into a small environment map from the seat, so steel, glass and polished floors reflect the room rather than a studio. A photo room instead hands its own HDR to the host (`SuiteScene.environment` → `SuiteHost.three.useEnvironment` → `Renderer.useLocalEnvironment`). The house's hemisphere light and sun are switched off for as long as the photo room is on screen, because the photograph already holds all of the room's light. The house's HDRI and lights come back when the suite closes.
